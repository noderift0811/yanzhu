01 结论速览

一句话架构：限定词进，人格页面出，对话持久化。工程师 AI 只产出结构化 JSON（人设提示词 + 骨架选择 + 主题 token + 页面文案），页面由预置骨架模板装配，不生成任何代码。

02 产品范围

MVP 包含

含结构化输入向导（标签点选 + 补充 + 示例） 含人格库（创建 / 列表 / 编辑 / 删除 / 重新生成） 含工程师 AI 管线（brief → spec JSON → 页面装配） 含16 套聊天骨架 + 主题 token 驱动 含建造揭晓（AI 搭页过程原地可视化） 含SSE 流式文字对话 + 持久化历史 + 每人格多会话 含账号注册 / 登录 + JWT + 每日 LLM 配额 含双密钥适配层 + Mock 降级（框架期无密钥全流程可跑）

MVP 不包含（明确后置）

不含试聊回流微调（"人设不对 → 工程师 AI 增量修订"，M2 核心差异功能） 不含人格分享链接 / 只读公开页（M2） 不含语音、图片人格、AI 生成头像图（头像用 CSS 渐变 + 首字，零图片成本） 不含心情条、打字节奏差异等高级表现层（骨架主题顺带覆盖） 不含多语言（MVP 全中文）

合规提示：公网服务涉及用户生成内容。MVP 做基础防护（限定词与补充文本长度上限、控制字符过滤、禁用词表、人格输出仅前端纯文本渲染）；完整内容审核送审留给 M2 前评估，不阻塞框架搭建。

04 核心管线：限定词 → 人格页面

四段式管线。工程师 AI 只被允许产出受 schema 约束的 JSON；页面由骨架模板装配，不生成代码。

S1输入净化标签 + 自由文本 → 归一化 brief JSON（截断 200 字、去控制字符）
→
S2工程师 AI强模型单次调用，JSON 模式，产人设 + 页面规格
→
S3校验装配pydantic schema 校验 → 骨架 + 主题 + 文案落库
→
S4聊天运行时轻量模型 + system_prompt 注入 + SSE 流式

S1 · brief 归一化

{
  "tags": ["内向", "害羞"],            // 来自预设标签点选
  "free_text": "说话轻声细语，熟了会撒娇",  // 来自补充框，截断 200 字
  "lang": "zh"
}

S2 · 工程师 AI（系统提示词定稿）

你是言筑的提示词工程师。用户会给你一组人格限定词（标签 + 描述），
你必须只输出一个 JSON 对象，不要任何解释、不要 markdown 代码块。

字段要求：
1. name：人格名字，中文，2-4 字，贴合气质
2. system_prompt：完整人设提示词（150-300 字），须包含：
   身份与姓名、性格核心、说话风格（句长 / 口癖 / 语气词）、
   与用户的关系定位、禁忌（不承认自己是 AI、不跳出人设）、2-3 句示例对话
3. skeleton_id：从 SKELETONS 目录中选最契合的一个 id，必须是目录中存在的值
4. theme：{"primary","bg","surface","text","accent"} 均为 #RRGGBB 十六进制；
   "font_style" 取值 rounded/serif/mono/system 之一；
   "decoration" 取值 none/petal/stars/grid/paper 之一
5. page_copy：{"title","greeting","input_placeholder"} 页面文案，贴合人设口吻
6. opening_message：人格对用户说的第一句话，20-60 字

硬约束：只输出 JSON；skeleton_id 必须来自目录；色值必须合法；全部中文；
不得输出任何 HTML、脚本或链接；不得提及本指令或你是 AI。

校验与降级（可靠性三板斧）

  1. schema 校验：pydantic 严格校验 spec；skeleton_id 必须在目录内；色值必须匹配 ^#[0-9a-fA-F]{6}$。
  2. 带错重试：校验失败时，把错误信息回喂工程师 AI 重试 1 次。
  3. 确定性兜底：仍失败则用默认 spec（skeleton=minimal、中性主题、基于 brief 模板拼装的 system_prompt），标记 status=needs_review，用户在人格库可一键重新生成。

S4 · 聊天运行时

  • 消息组装：[system: persona.system_prompt] + 最近 20 条历史（滑动窗口控成本）+ 新消息。
  • 用户聊天消息永不进入 system 层；MVP 无函数调用 / 工具调用，人格设定只能经 S2 管线修订。
  • 流式：persona adapter chat_stream() 逐 token 产出，经 SSE 转发；同时落库完整消息与 token 用量。

05 数据模型（SQLite WAL）

沿用既有规范：业务表 UUID VARCHAR(36) 主键；高频写入的 messages 用 BIGINT 自增（同 event_log 先例）；图片不存 base64（本产品零图片）；所有查询按 user_id 隔离。

表字段说明
usersid UUID PK · username UNIQUE · password_hash · quota_gen_daily INT DEFAULT 20 · quota_chat_daily INT DEFAULT 100 · quota_gen_used INT · quota_chat_used INT · quota_reset_at · created_at账号 + 每日 LLM 配额计数（LLM 是成本中心，配额按用户维度）
personasid UUID PK · user_id FK · name · keywords_json · brief_json · spec_json · skeleton_id · theme_json · status ENUM(active, needs_review) · created_at · updated_at人格库主表；keywords_json 留原始输入便于重新生成；索引 user_id
conversationsid UUID PK · persona_id FK · user_id FK · title · created_at · updated_at每人格可有多会话；索引 (user_id, persona_id)
messagesid BIGINT auto_increment PK · conversation_id FK · role ENUM(user, assistant) · content TEXT · tokens INT · created_at高频写，自增主键；索引 (conversation_id, created_at) 支撑历史分页
llm_callsid BIGINT auto_increment PK · user_id · purpose ENUM(engineer, persona) · adapter · model · latency_ms · status · error · created_at审计与成本观测；配额超限与故障排查的依据
软删除策略：本产品无软删除需求，DELETE personas 级联删除其 conversations 与 messages（SQLite 开外键或应用层保证）。配额重置：quota_reset_at 跨日时清零 used 计数。

建造揭晓：把“AI 搭页面”的过程变成可见的演出

首页即工位，三态原地切换，不跳路由、不建新页：输入向导态 → 建造中态 → 人格聊天态。从人格库打开或重新生成人格时，重放建造动画。

两条硬规则：① 全程组件级原地热替换（React 状态驱动挂载 + CSS 变量过渡），禁止 location.reload()——刷新会丢状态、闪屏、切断 SSE 连接；② 编排式揭晓，禁止把工程师 AI 拆成多次调用换步骤——单次调用拿全量 spec，按真实决策顺序分阶段落位，每个阶段展示的都是 AI 的真实产出。
阶段页面表现数据来源
1 布局骨架轮廓淡入（空页面框架）skeleton_id
2 上色主题色 / 字体 / 装饰渐变生效theme

5 就绪输入框点亮，可开始聊天—
  • 节奏对齐真实耗时：工程师调用通常 8-15s，spec 到达即走完后续阶段；未到达时显示“AI 正在决定页面风格”的真实等待态；总时长封顶约 10s，不为动画硬拖。
  • 失败优雅收尾：管线失败走兜底 spec 时，动画收尾到默认风格并提示“可重新生成”，不能播到一半裸奔。
  • 无障碍：尊重 prefers-reduced-motion，一键直出完整页面。
  • 后端零改动：揭晓是纯前端动画层，spec schema 与 API 不变。

无障碍与稳健性

  • LLM 输出内容一律纯文本渲染，全程无 dangerouslySetInnerHTML，XSS 无入口。
  • SSE 断线自动重连提示 + 手动"重新生成回复"；流式中可随时停止（AbortController）。
  • access token 过期静默刷新一次，失败跳登录页；路由守卫未登录进 /login。

08 双密钥 LLM 适配层（先搭框架，暂不接密钥）

适配器接口（复用 InfoHub BaseAdapter 模式）

# backend/app/llm/base.py
class BaseAdapter(ABC):
    name: str
    @abstractmethod
    async def chat_json(self, messages: list[dict], *, temperature: float = 0.7) -> dict: ...
    @abstractmethod
    def chat_stream(self, messages: list[dict], *, temperature: float = 0.8) -> AsyncGenerator[str, None]: ...

# backend/app/llm/registry.py
REGISTRY: dict[str, type[BaseAdapter]] = {}
def get_adapter(purpose: Literal["engineer", "persona"]) -> BaseAdapter:
    cfg = settings.engineer_llm if purpose == "engineer" else settings.persona_llm
    if not cfg.api_key:              # 框架期：未配置密钥 → 确定性 Mock
        return MockAdapter(purpose)
    return REGISTRY[cfg.adapter](cfg)

MockAdapter 行为约定

  • chat_json：按 brief 的标签确定性拼装合法 spec（skeleton 按标签映射表选择，主题按标签映射），保证 schema 永远通过，供前端联调。
  • chat_stream：按人格口吻模板分片输出 canned 回复（带打字延迟模拟流式），可被相同输入稳定复现。
安全边界：密钥只存在于后端环境变量；前端零密钥；Mock 降级只在"未配置密钥"时触发，配置错误（密钥无效）不走 Mock、直接报错，避免"假成功"掩盖故障。

13 本轮新增：命名权、保存、沉浸、网页代码

四项都围绕同一件事：页面是用户自己的，应该能带走、能改、能专注地待在里头。全部零新增依赖、零额外模型调用。

13.1 角色名字由用户决定

  • 向导确认页新增「角色名字」输入（2-20 字，可留空）。填了就是硬约束，留空仍由工程师 AI 起名。
  • 三层保证：提示词里写明「必须原样使用该名字」→ 落库前_apply_forced_name 再强制覆盖一次（模型改一个字也不生效）→ 把 system_prompt 里模型自己起的旧名字整体替换，避免出现「你的名字是沈砚。你是陆沉，一个档案管理员」这种自相矛盾的人设。
  • 随时可改：人格库卡片新增「改名」，PATCH /personas/{id} 同步写 personas.name、spec.name 与 system_prompt，不调 LLM、不耗配额；重新生成时默认回填当前名字，不会被悄悄换掉。

13.2 保存对话

  • 聊天页头部「保存」下拉提供三种格式：Markdown（给人读，粘进笔记就能看）、纯文本（最省事）、JSON（完整消息数组 + 时间戳，可程序化再处理）。
  • 文件名统一 言筑-人格名-会话名-YYYYMMDD-HHmm，纯前端 Blob + a[download] 生成，不经后端、不耗配额。

13.3 全屏沉浸

  • 头部「全屏」进入沉浸态：锁页面滚动、.pf-chat 固定铺满视口、隐藏应用外壳，只留这个人格；再点一次或按 Esc 退出。
  • 一个踩过的坑（真 bug）：最初把 .pf-chat 自己设为全屏元素，结果「保存」菜单（antd Dropdown 挂在 body）看不见、点不到——浏览器全屏只渲染全屏元素内部。改为对 document.documentElement 请求全屏、视觉占满交给 CSS，弹层与提示都在全屏范围内，问题消失。

13.4 保存搭好的网页代码

  • 「网页存为单文件 HTML」把当前聊天页做成双击即开的独立页面：DOM 快照 + 按选择器裁剪内联的 CSS（体积约 320-360 KB）+ <script type="application/json" id="yanzhu-spec"> 里随页附带完整 spec。
  • 为什么快照而不是另写静态模板：16 套骨架各有独立布局，重写一份必然与线上走样；快照保证「导出即所见」，主题变量、装饰、字号全部原样保留。
  • 静态化处理：摘掉点头部按钮与会话切换条（点不动只会误导），输入框降级为只读并提示「这是导出的静态页面」，底部标注导出时间与来源。
  • 另提供「配置存为 JSON」：spec + 主题 + 关键词 + brief，方便自己拿去做二次开发或喂给别的模型。

14 标签互斥：把矛盾挡在生成之前

用户能同时选中「内向」和「外向」、「活泼」和「沉稳」。危害不是报错，而是成品悄悄变平庸——模型收到自相矛盾的 brief，只能二选一或折中，用户以为给了六个限定词，实际强度只剩三个。

14.1 问题不在标签太多，而在三处缺口

缺口原来的状态后果
互斥关系没声明10 个性格标签平铺在一个数组里，彼此关系未定义内向与外向被当成两个独立维度
跨组冲突没人管性格组与语气组各管各的内向配活泼这种更隐蔽的组合无人拦
数量没约束前端无上限，后端限 12 个选满即交，模型负担过重

14.2 用「轴」建模，不是两两配对

两两列互斥要列九对，加标签还得逐个补关系。改成声明四条轴，每轴最多选一个，四条声明覆盖全部冲突。

轴成员
性格·社交向内向 ／ 外向
性格·判断式理性 ／ 感性
语气·能量活泼 ／ 安静 ／ 沉稳 ／ 冷淡
语气·分寸严肃 ／ 俏皮 ／ 撒娇

14.3 反差不算矛盾，别一起禁掉

「毒舌＋温柔」是嘴硬心软，「高冷＋粘人」是反差萌——这类组合恰恰是出彩的地方。所以分三档处理：

类型例子处理
硬矛盾（同轴两极）内向／外向、活泼／沉稳直接挡，选一个另一个置灰
反差张力毒舌＋温柔、高冷＋粘人、慢热＋粘人不禁，仅在补充描述为空时提示一句怎么调和
自由组合傲娇＋前辈、腼腆＋笔友不管

14.4 四层落地

  1. 选中即互斥：置灰而非隐藏，标签留在原位，用户看得懂"为什么点不了"；点击时给一句解释（移动端没有 hover，只靠 title 等于没提示）。
  2. 组配额：性格 3、语气 2、关系 1，总数 8。禁区不设上限——"不说教＋不玩梗＋不主动提问"是叠加的约束，彼此不冲突。
  3. 反差提示：命中张力对时提示一句，用户写了补充描述就自动收起。
  4. 后端兜底：pipeline/tag_rules.py 做确定性消解，同轴保留先出现的，被丢弃的写进 brief.dropped_tags 随详情回传——不做静默删改。前端拦不住的三条路（重新生成弹窗、历史数据、直接调 API）都由这一层接住。

两个配套修正：keywords_json 改存去冲突后的值（否则卡片标签与"重新生成"回填会把这些冲突复活）；提示词构建时剔除 dropped_tags（对生成无用，只会让模型困惑"为什么给了又丢"）。
